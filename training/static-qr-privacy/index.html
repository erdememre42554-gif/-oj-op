Static QR codes and the privacy of a printed square

A static code encodes the payload itself. A dynamic code routes every scan through a redirect. Only one of them can count you, and only one of them can expire.

A QR code is a container, not a link shortener. The symbol holds a string; the string can be a URL, a Wi-Fi credential, a phone number, or plain text. What happens after the scan depends entirely on what the string contains — and that is where the privacy question lives.

Two kinds of QR code

Static. The payload is encoded directly in the modules. If the string is https://example.com/menu, that address is in the symbol. Anyone with a decoder can read it without contacting anything. There is no server in the loop, nothing to expire, and no way to know how many times it was scanned.

Dynamic. The symbol holds a short redirect URL such as https://qr.example/8f3k. The redirect service looks up the destination and forwards the scanner. This makes the code editable after printing, and it makes every scan countable — the service sees an IP address, a timestamp, a device type, and often an approximate location.

Both are legitimate. A restaurant that reprints its menu weekly may genuinely need a dynamic code. The problem is that dynamic codes are frequently used where the tracking is invisible to the person scanning, and the printed square gives no clue which kind it is.

What a static code cannot leak

The code itself stores no identity. Two people scanning the same menu code receive exactly the same string, and the paper has no idea who scanned it. The only information disclosure is whatever the destination URL does when it loads: ordinary web tracking, which is governed by that site’s own policy.

That is a narrower promise than “anonymous”. If the payload is https://example.com/?table=12, the restaurant knows table 12 was scanned, and the site’s analytics do the rest. The QR format simply is not the tracking mechanism.

Reading a code before you follow it

The practical defence is to decode first and open second. A scanner that opens URLs automatically removes the moment where you could have looked at the destination.

The DayGrid QR reader shows the raw payload and its type — URL, Wi-Fi, mailto:, tel:, vCard, or plain text — without navigating. If the payload starts with javascript: or data:, it is flagged rather than offered as a link, because a scanner that passes arbitrary strings to a browser can be used to run script in the page’s origin.

A useful habit for codes you did not print yourself:

  • Decode on a device where opening the link is a deliberate second action.
  • Check the hostname, not just the visible words in the payload.
  • Be suspicious of shorteners on physical stickers, especially ones pasted over older codes.

Camera access without a recording

Live scanning needs getUserMedia, which triggers a permission prompt and, in most browsers, requires HTTPS. Once granted, frames arrive as a video stream. What happens to them is entirely up to the page.

The local implementation draws each frame to an offscreen canvas, reads the pixels, and discards both. Nothing is uploaded and nothing is written to storage. The camera track is stopped when a code is found or when you press stop, which turns off the recording indicator.

That is a claim you can audit: open DevTools → Network, start the camera, and watch. There is no stream upload, because there is no code that could encode one.

Why the tool does not track scans

Scan counting requires a server in the middle, and a server in the middle is exactly what a local-only tool promises not to have. Adding “scan analytics” would mean either lying about the architecture or routing every scan through infrastructure that sees the user.

For a static code, the honest answer is that you cannot count scans. If you need the count more than you need the privacy, use a dynamic code from a provider that says so plainly on the printed material.
