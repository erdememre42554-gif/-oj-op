QR error correction is a budget, not a guarantee

What L, M, Q and H actually spend, why a denser code is harder to scan, and how module size and quiet zone decide whether a printed code works.

A QR code is a grid of black and white modules with three finder squares and a lot of redundancy. Part of that redundancy is deliberate: the standard lets you spend some of the payload space on error correction, so a code still decodes when part of it is dirty, printed badly, or covered by a logo. Understanding that budget is what separates a code that scans from a code that gets peeled off a wall.

The four levels

The QR standard defines four error-correction levels. The percentages are the fraction of codewords that can be restored, not a promise about physical damage.

Level Recovery budget Typical use
L ~7% Clean digital display, maximum data
M ~15% General print, screens, default choice
Q ~25% Stickers, labels, codes near a logo
H ~30% Harsh environments, heavy logo overlay

Two things follow. First, higher correction means fewer data modules available, so the encoder must use a larger version — a denser grid — for the same payload. Second, density hurts scanning more than redundancy helps in many real cases. A version 10 code at level H has more modules than a version 6 code at level M, and each module is smaller at the same print size.

For a URL of ordinary length on a screen or a clean menu, M is the right default. Reach for Q when the code will be handled, and H only when you are deliberately covering part of it.

Quiet zone: the margin nobody prints

Every QR symbol requires a quiet zone of four modules of light colour on all sides. The quiet zone is not padding for aesthetics; it is how the decoder finds the symbol’s edges. Print a code flush against a dark border and the scan often fails at the boundary even though the modules are perfect.

This is the most common production mistake. A designer crops the exported PNG to the black edge to make it “fit”, the surrounding artwork is dark, and the code stops working on a third of phones. Export with the margin included, and if you must place a code on a coloured background, keep at least four modules of white around it.

The DayGrid QR generator always includes a margin of two to four modules depending on the size setting and draws it in the background colour you choose. If you set the background to something dark, the contrast between modules is what matters, not the colour name.

Module size and viewing distance

A QR code does not have a resolution; it has a module size. The camera needs enough pixels per module to distinguish black from white. A rough working rule for print is:

  • Minimum 2 cm wide for a short payload scanned at 20–30 cm.
  • 3–4 cm for a URL with a query string.
  • Larger when the code is behind glass, laminated, or printed on fabric.

The relationship is not linear in payload length: doubling the payload roughly doubles the module count in each dimension at a fixed error-correction level, which quadruples the area needed for the same module size. A 300-character payload printed at 2 cm will not scan reliably no matter which phone you use.

Wi-Fi payloads

The de-facto Wi-Fi format is a single string:

WIFI:T:WPA;S:NetworkName;P:password;H:false;;

T is the security type (WPA, WEP or nopass), S the SSID, P the password, and H whether the network is hidden. Semicolons, commas, colons and backslashes inside a value must be escaped with a backslash, which is why a password containing ; breaks naively generated codes. The trailing double semicolon is part of the format; some scanners tolerate its absence, some do not.

A Wi-Fi code is a credential printed in public. Treat it like writing the password on the router: fine for a guest network that is rotated regularly, a bad idea for the network your laptop uses.

Testing before you print a thousand

Generate the code, then test it with the actual scanner and the actual distance. Three checks catch most failures:

  1. Scan from the exported file, not the on-screen preview. Canvas previews are often sharper than the print.
  2. Scan a printed proof at final size, on the final material, under the final lighting.
  3. Scan with the oldest phone you expect to support. Decoders differ, and older cameras have less tolerance for small modules.

If a code fails, increase the module size before increasing the error-correction level. Bigger modules fix more scans than more redundancy does.
