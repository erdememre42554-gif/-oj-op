Randomness is not the same as looking complicated

Password strength is arithmetic on an alphabet and a length. Character-class theatre adds nothing, and Math.random is the wrong source for a secret.

A password like P@ssw0rd!2026 looks complicated. It is also one of the first strings any cracking tool tries, because the substitutions are the ones everybody makes. Meanwhile a six-word passphrase made of ordinary lowercase words looks weak and can be far stronger. The difference is not visual. It is the size of the space an attacker has to search.

Entropy is arithmetic, not aesthetics

The strength of a generated password is the base-2 logarithm of the number of equally likely passwords the generator could have produced. If you draw twelve characters independently from a 74-symbol alphabet, the space is 74¹² and the entropy is 12 × log₂(74) ≈ 74.5 bits. Nothing about the result’s appearance changes that number.

This is why character-class rules are a poor proxy. “Must contain a symbol, a digit and an uppercase letter” is a constraint on the output, and constraints that are predictable reduce the space slightly rather than increasing it. A generator that picks from a fixed pool of 74 symbols already produces symbols, digits and uppercase letters at the expected rate. Forcing one of each is a convenience for sites with arbitrary rules, not a strength improvement.

The honest formula is:

entropy ≈ length × log2(alphabet size)

Everything else — whether the string “looks random” — is noise. A good generator will tell you the alphabet size and the length so you can check the arithmetic yourself.

Why Math.random is the wrong tool

JavaScript has two random sources and they are not interchangeable.

Math.random() is implemented by the engine and is not required to be cryptographically secure. V8’s implementation is a fast xorshift-style generator seeded from a small amount of state. Observing enough outputs can allow an attacker to reconstruct that state and predict every subsequent value. For a dice roll in a game, that is fine. For a password, it is a structural weakness that no amount of length can repair.

crypto.getRandomValues() draws from the platform’s cryptographic random source. It fills a typed array with bytes the operating system considers unpredictable, and it is the API browser and Node documentation point to for anything security-relevant. The call is synchronous, costs microseconds, and is available in every browser that can run this site.

There is a second, subtler trap: modulo bias. If you take a random 32-bit integer and compute value % 62 to pick from a 62-character alphabet, the first few characters are slightly more likely than the rest, because 2³² is not divisible by 62. The bias is tiny, but it is free to remove. The correct approach is rejection sampling: compute the largest multiple of the alphabet size that fits in the source range, discard values at or above it, and only then take the modulus.

const limit = Math.floor(0x100000000 / max) * max;
let value;
do {
  crypto.getRandomValues(buffer);
  value = buffer[0];
} while (value >= limit);
return value % max;

A generator that skips this step is still usable, but it is not doing the arithmetic it claims.

What the estimate assumes

An entropy figure is conditional. The number next to a generated password assumes:

  1. The characters were drawn independently and uniformly.
  2. The attacker knows the generator’s alphabet and length.
  3. The attacker does not know the specific random draw.

The third assumption is the whole point. The first two are why publishing the method is safe: Kerckhoffs’s principle says a system should remain secure when everything except the key is public. A generator that relies on a secret alphabet is weaker than one that publishes its alphabet and draws uniformly.

What the estimate does not cover is the rest of the password’s life. If the site stores it in plaintext, if it is reused across accounts, if it is typed into a phishing page, or if it is read over your shoulder, the entropy is irrelevant. NIST’s authentication guidance is explicit that verifiers should store passwords with a salted, slow hash and should not impose composition rules; the strength has to come from the secret itself and from the system that stores it.

Checking a generator’s claim

You can verify most of this in the browser without trusting the page.

Open DevTools → Network, clear the log, and generate. No request should carry the output. Then open the console and confirm that the implementation uses crypto.getRandomValues rather than Math.random — the call is visible if the code is not minified, and the tool’s own documentation should say which it uses.

For the arithmetic, pick an absurd length: 128 characters from the same 74-symbol alphabet is about 795 bits. If a tool reports a much smaller number, it is either using a smaller alphabet than advertised or applying an arbitrary cap.

None of this makes a password memorable. That is a separate problem, and it is why passphrases exist.
